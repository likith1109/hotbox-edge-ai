Mission 4 calculation conventions and interpretation

For each Linear(a,b): parameters = a*b+b; float32 parameter bytes = 4*(a*b+b); ideal int8 parameter bytes = a*b+b; MACs = a*b. Bias additions and ReLU operations are not weight MACs. Summing the selected layers gives 385 parameters, 1540 float32 bytes, 385 ideal int8 bytes, and 352 MACs.

For 5->w->w->1, P(w)=w^2+8w+1=(w+4)^2-15 and MACs=w^2+6w. The same describe_model function used by /model_info generates width_table.csv. Closed-form formulas and exhaustive width search independently verify its values and boundaries.

The existing API interprets the assignment's SRAM limit as 300 KiB (307200 bytes), and PSRAM as 8 MiB (8388608 bytes). For parameter storage only, maximum widths are 273 float32 and 550 ideal int8. At the next widths, 274 and 551, weights plus biases no longer fit. width_limits.json includes exact byte inequalities and the stricter decimal 300000-byte interpretation (269 float32 and 543 ideal int8). Whole-program limits will be lower after activations, stack and runtime are included.

Peak activation estimate: one prediction, two 16-slot buffers; input 5 slots and layer-1 output 16 coexist (21 elements), then hidden input 16 and hidden output 16 coexist (32), then hidden input 16 and final output 1 coexist (17). ReLU and normalisation operate in place; old inputs are released before reuse. Peak is 32 float32 elements = 128 bytes (32 bytes for hypothetical int8 activations). This is a native buffer schedule, not PyTorch process RAM. If all input/hidden/output tensors are retained in separate allocations, reserve (5+16+16+1)*4 = 152 bytes instead. Kernel scratch, accumulators, alignment, stack and allocator caches are excluded. Two saved normalisation vectors add 40 float32 bytes separately, giving 1708 bytes for selected f32 parameters + scheduled activations + normalisation statistics, before runtime/scratch/code.

Throughput assumption: Espressif's optimized ESP32S3 O2 dsps_dotprod_f32 benchmark reports 432 CPU cycles for 256 float32 terms. At an assumed 240 MHz this corresponds to 142.22 million MAC/s for that long-vector microbenchmark. Choose 100 million MAC/s as an explicit rounded-down throughput assumption. Estimated selected-model arithmetic time = 352 / 100000000 seconds = 3.52 microseconds = 0.00352 ms. This is not a measured rate for short length-5/16 dense kernels and is not a full prediction latency guarantee. Smaller vectors, tails, call setup, biases, ReLU, scaling and I/O can dominate. CPU clock and dot-product benchmark sources are in sources.json. Actual board latency is unmeasured; saved Codespace inference medians are measurements of a different runtime.
